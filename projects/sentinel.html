Sentinel AI Task Processor

Distributed background job processing system for asynchronous AI tasks. Redis Streams for queueing, PostgreSQL for persistence, Google Gemini for inference, and real-time monitoring via SSE — all containerized with Docker.

Source Code
Python FastAPI Redis Streams PostgreSQL Google Gemini Docker Prometheus SSE

The Problem

AI inference is slow and unpredictable. If your API blocks while waiting for a model response, every client stalls. Retries hammer the provider, rate limits bite, and you have zero visibility into what's queued, running, or failed.

Sentinel solves this by decoupling submission from processing. The API accepts a task and returns immediately. A separate worker pool consumes from a Redis Stream, calls Gemini, persists results, and pushes real-time status updates to connected browsers — all with exactly-once delivery semantics and full observability.

How Data Flows

Write Path (Client submits a task)

Step 1 — Accept

POST /tasks validates the payload, checks the Redis rate limiter, generates a Snowflake ID (64-bit, no DB round-trip), and calls XADD to push the task onto the Redis Stream. Returns the task ID immediately — the client never waits for inference.

Step 2 — Process

The worker service reads from the stream via XREADGROUP (consumer group ensures each task is delivered exactly once). It calls the Google Gemini API, handles errors and retries, then upserts the result into PostgreSQL.

Step 3 — Notify

After persistence, the worker publishes a status event to Redis Pub/Sub. The monitor service picks it up and fans it out to all connected browsers via Server-Sent Events. The UI updates in real time — no polling needed.

Read Path (Client checks status)

Step 1 — Query

GET /tasks/{id} reads directly from PostgreSQL. For listing recent tasks, GET /tasks returns the latest entries ordered by creation time.

Step 2 — Retry

POST /tasks/{id}/retry resubmits a failed task back to the Redis Stream with the same ID. The worker picks it up again — idempotent upserts make this safe.

Why These Choices

DecisionWhyTradeoff
Redis Streams over Celery/RabbitMQ Built-in consumer groups, message acknowledgement, and backpressure. No extra broker — Redis already handles rate limiting and pub/sub. Less ecosystem tooling than Celery. No built-in periodic tasks. Worth it for the simplicity of a single Redis dependency.
Snowflake IDs 64-bit, time-sortable, globally unique without a DB sequence. Generated at the API layer — no round-trip before queuing. Requires clock synchronization across nodes. Fine for a single-node setup; in multi-node you'd add a machine ID.
SSE over WebSockets Unidirectional updates are all we need (server → browser). SSE is simpler, auto-reconnects, works through HTTP proxies. No bidirectional channel. Clients still use REST for commands. That's the right split here.
PostgreSQL as source of truth ACID guarantees on task state. Redis is ephemeral by design — if it restarts, PG has the complete history. Supports complex queries for analytics. Extra write on every task completion. Worth it — Redis Streams aren't designed for long-term storage.
FastAPI Async-native, automatic OpenAPI docs, Pydantic validation. Fits naturally with async Redis and DB clients. Python's GIL limits CPU-bound throughput. Not a concern here — the bottleneck is Gemini API latency, not CPU.
Three separate services API, Worker, and Monitor scale independently. Worker can be scaled horizontally — consumer groups handle partitioning. Monitor is stateless. More containers to manage. Docker Compose handles this in dev; in prod, Kubernetes would orchestrate.

Key Engineering Details

  • Exactly-once processing — Redis consumer groups with XREADGROUP + XACK. Each task is delivered to one consumer. Acknowledgement happens only after PG write succeeds. Unacked messages are reclaimed on restart.
  • Rate limiting — Sliding window counter in Redis. Configurable via RATE_LIMIT and RATE_WINDOW env vars. Rejects with 429 before any work is done.
  • Health checks (three tiers) — /health (full system), /health/live (Kubernetes liveness), /health/ready (readiness — checks Redis + PG connectivity).
  • Prometheus metrics — Exposed at /metrics on each service. Task counts, processing latency histograms, error rates, queue depth.
  • Structured logging — JSON or text format via env config. Correlation IDs flow through the entire request lifecycle.
  • Graceful error handling — Custom exception hierarchy in core/exceptions.py. Gemini failures don't crash the worker — tasks are marked failed and available for retry.
